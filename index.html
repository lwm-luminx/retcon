retcon

Field-level history for every versioned table, with live tables kept as a projection of it. Edits are attributed changesets; proposals wait for review like pull requests; an actor’s damage reverts without losing the work that came after it; and redaction scrubs a value from history while history still verifies.

gem 'retcon'

GitHub · RubyGems · Changelog

Getting started

retcon keeps a full, field-level history of the Active Record models you choose, on PostgreSQL. Every save is attributed to someone and grouped into a changeset. Changes can also be proposed and applied later after review, like a pull request. When something goes wrong (a bad delete, a vandal, a privacy request), you repair it with a new changeset instead of restoring a backup, and the good work that came after it stays.

Your live tables don't move and don't get slower. They become a projection of history: written in the same transaction as the history rows, and rebuildable from them at any time.

Install

# Gemfile
gem 'retcon'

retcon needs Ruby 3.3+, Active Record 7.1+ and PostgreSQL 15+ through the pg adapter.

Create the tables

One migration creates retcon's shared tables, and one call per table versions it:

class InstallRetcon < ActiveRecord::Migration[8.0]
  include Retcon::Schema

  def change
    create_retcon_tables   # retcon_actors, retcon_changesets and the retcon_seq sequence
    version_table :venues  # retcon_venues, three columns on venues, and a trigger
    version_table :events
  end
end

version_table creates the history table retcon_venues, adds retcon_seq, retcon_digest and retcon_dirty to venues, and installs a trigger that marks rows written outside retcon (see Drift and bulk writes).

Version a model

class Venue < ApplicationRecord
  include Retcon::Model
end

That's all a model needs. Every column is versioned except the primary key, timestamps, lock_version, counter caches (*_count) and retcon's own columns. Models covers choosing fields.

Rows that existed before retcon have no history yet. Give them a starting point once, after the migration:

Venue.retcon_genesis!   # one "Genesis" changeset per batch of 500 rows

Make attributed changes

Wrap changes in Retcon.as to say who made them:

Retcon.as(current_user) do
  venue.update!(name: 'The Eagle', phone: '555-0100')
end

Saves work exactly as before: validations and callbacks run, and save still returns true or false. retcon adds a changeset with the user as its author, a version row for each changed field, and the record's new retcon_seq.

Group several saves into one changeset with a message:

Retcon.changeset(actor: current_user, message: 'New season') do
  venue.update!(hours: { 'tue' => '4pm-2am' })
  venue.events.create!(name: 'Drag Bingo')
end

Read history

venue.retcon_versions          # every version row, oldest first
venue.retcon_heads['phone']    # the current version of a field: seq, value, row_id (blame)
Retcon::Changeset.last.author  # who made the last change
Retcon::Changeset.last.changes # {[Venue, id] => {'name' => 'The Eagle', ...}}
Venue.retcon_state(venue.id)   # the record as history says it is

Models

Include Retcon::Model in any Active Record model whose table was versioned with version_table. Settings go in a versioned block:

class Venue < ApplicationRecord
  include Retcon::Model

  versioned do
    ignore :view_count, :search_vector
    merge :tags, :set_union
    scope(&:audience_id)
  end
end

Versioned fields

By default every column is versioned except:

  • the primary key and retcon's own columns (retcon_seq, retcon_digest, retcon_dirty);
  • created_at, updated_at and lock_version;
  • counter caches: any column ending in _count.

ignore leaves more out. only names the versioned fields outright instead:

versioned do
  only :name, :address, :phone
end

Venue.retcon_config.tracked_fields lists the result. A save that changes only untracked fields writes no history and no changeset, so view counters and search vectors cost nothing.

Fields keep their types through history. Values are stored as JSON: strings, numbers, booleans, arrays and jsonb as they are; dates, times and decimals as strings; anything else through as_json. They are cast back through the attribute's type when read.

Scope

scope gives every changeset about a record a scope string, such as the tenant or audience it belongs to. Reverts and reviews can then be limited to it:

versioned do
  scope { |venue| venue.audience_id }
end

Retcon::Changeset.where(scope: audience.id.to_s)
Retcon.revert_actor(vandal, actor: staff, scope: audience.id.to_s)

A changeset takes the scope of the first record it writes, unless Retcon.changeset(scope:) sets one.

Merge strategies

When a proposal changes a field that someone else changed after the proposal's base, it conflicts. A merge strategy can settle that instead:

  • :replace (the default): it conflicts.
  • :set_union: for array fields, the result keeps every element either side has. Two people tagging the same venue both get their tags.
versioned do
  merge :tags, :set_union
end

The merged value is written as one more version in the applied changeset, after the proposed one.

Schema versions

schema_version, rename_field and upcast keep old history readable when columns change. See Schema evolution.

Associations and callbacks

Saves and destroys are wrapped whole, so autosaved associations and dependent: :destroy children join the same changeset as their parent. Your callbacks run on ordinary saves. When retcon writes live rows itself (applying a proposal, reverting, rebuilding), it validates the record but skips callbacks. Check Retcon.replaying? in a callback that has side effects you never want to repeat, such as sending a notification:

after_save :notify_followers, unless: -> { Retcon.replaying? }

Instance and class methods

Method Returns
record.retcon_versions every version row of the record, oldest first, proposals included
record.retcon_heads {field => Head} with the newest applied version of each field
record.retcon_drifted? whether the live row was written outside retcon
record.retcon_base = seq the base version the next save is checked against
record.retcon_on_conflict = :skip leave conflicting fields out of the next save
record.retcon_conflicts the fields the last save left out
Model.retcon_state(id) {'exists', 'seq', 'attributes'} as history says, or nil
Model.retcon_revive!(id, actor:) brings a deleted record back with its id
Model.retcon_rebuild!(id) rewrites the live row from history
Model.retcon_sweep! catches up rows written outside retcon
Model.retcon_genesis! gives pre-retcon rows their first history

Changesets and actors

Changesets

A changeset is one logical change: version rows across any number of records and tables, with an author, a message and, once someone applies or decides it, a committer. Changesets are never deleted. Reverts and redactions are changesets too, so they can be inspected and undone like anything else.

Column Meaning
kind edit, proposal, genesis, catch_up, import, revert, redaction
state applied, proposed, rejected, withdrawn, amended
author / committer who wrote it, and who applied or decided it
applied_seq its place in retcon's global order of application
parent the changeset this one amends, or the revert a review proposal came from
scope the tenant or audience it belongs to (see Models)
message, metadata free text, and a jsonb hash for your own keys

Every save outside Retcon.changeset gets a changeset of its own. Inside one, every save joins it, nested blocks included, and the whole block runs in one database transaction:

changeset = Retcon.changeset(actor: staff, message: 'Merge duplicate venues', metadata: { 'ticket' => 'OPS-12' }) do
  keep.update!(phone: dupe.phone)
  dupe.destroy!
end
changeset.records   # [[Venue, keep.id], [Venue, dupe.id]]
changeset.versions  # the version rows, in write order
changeset.changes   # {[Venue, keep.id] => {'phone' => '555-0100'}}

A block that changes nothing leaves no changeset and returns nil.

Global order

applied_seq comes from one PostgreSQL sequence, retcon_seq, shared by every versioned table. Every version row of an applied changeset carries the same seq, and the live row's retcon_seq is the seq of the last changeset that wrote it. That is what conflicts are checked against, and what lets reverts and rebuilds replay history in order.

Actors

History stores actor ids, never names or emails. An actor stands for a record, or is named:

Retcon.as(current_user) { ... }                         # a record: a User, a device grant, an API client
Retcon.as(Retcon::Actor.named('import', 'facebook')) { ... }
Retcon.as('nightly-cleanup') { ... }                     # a String names a system actor

Retcon::Actor.resolve turns any of these into an Actor row, creating it the first time. Record actors are of kind user unless you map the class:

Retcon::Actor.kinds = { 'VenueDeviceGrant' => 'device' }

actor.record finds the record again; actor.label is how to show it (its pseudonym once redacted).

Agents

When software acts for a person (an assistant, a moderation bot acting on a report), attribute the change to both:

Retcon.as(glam_bot, on_behalf_of: host) { event.update!(status: 'cancelled') }

The changeset's author is an agent actor that points at the person it acted for (on_behalf_of). Reverting the agent's changes, or the person's, finds them either way.

Unattributed saves

Saves with no actor set are attributed to Retcon::Actor.system ("unattributed"), so nothing breaks while you add Retcon.as around your write paths. Turn that off once they're covered:

Retcon.allow_unattributed = false   # saves with no actor raise Retcon::Error

A common place for Retcon.as is a controller around_action, or the GraphQL context for mutations.

Events

retcon publishes through ActiveSupport::Notifications as <name>.retcon, with the changeset in the payload:

Event When
proposal_opened a proposal (or an amended one) is opened
changeset_applied a proposal is applied
proposal_rejected a proposal is rejected
revert_conflict a revert left same-field overlaps in a review proposal
redacted a redaction is written 
Retcon.on(:proposal_opened) { |changeset| ReviewQueue.route(changeset) }

This is how you route proposals to reviewers, for example to a moderation host or a staff queue.

Conflicts

Two people open the same venue. One fixes the phone number, the other the hours. Both save. With retcon both changes stay: conflicts are checked per field, and only when someone else changed that same field to a different value after the version you started from.

The base version

Every live row carries retcon_seq, the seq of the last changeset that wrote it. A record remembers the retcon_seq it was loaded with; that is its base. On save, retcon:

  1. locks the live row (SELECT ... FOR UPDATE) for the rest of the transaction;
  2. catches up any change written outside retcon since (see Drift);
  3. compares each changed field's newest version with the base.

A field conflicts when its newest version is newer than the base, came from someone else's change, and holds a value different from the one being saved.

mine = Venue.find(id)      # base: seq 41
theirs = Venue.find(id)
Retcon.as(bob) { theirs.update!(phone: '555-0199') }   # seq 42

Retcon.as(alice) { mine.update!(hours: '4pm-2am') }    # fine: hours didn't move
Retcon.as(alice) { mine.update!(phone: '555-0100') }   # Retcon::Conflict: phone changed at seq 42

Saving the value that's already there never conflicts.

Web forms: an explicit base

A record loaded inside the request that saves it has a base from moments ago. For an edit form, the base that matters is the one the person saw when the form was rendered. Put the record's retcon_seq in the form and give it back:

# the form: hidden_field :retcon_seq
venue.retcon_base = params[:venue][:retcon_seq].to_i
venue.update!(venue_params)

retcon_base also takes {field => seq} for clients that track versions per field. It applies to the next save only.

Handling a conflict

By default a conflict raises Retcon::Conflict and nothing is saved:

rescue Retcon::Conflict => e
  e.conflicts.each do |c|
    c.field     # 'phone'
    c.current   # what is there now: '555-0199'
    c.proposed  # what this save wanted: '555-0100'
    c.base_seq  # the version the edit started from
    c.head_seq  # the version that moved it
  end

Show the person both values and let them choose. Or save what you can and report the rest:

venue.retcon_on_conflict = :skip
venue.update!(phone: '555-0100', hours: '4pm-2am')
venue.retcon_conflicts   # [FieldConflict(phone)]: hours saved, phone left as it was

Skipped fields are put back to their database value on the record.

Proposals

Proposals record their base when they're opened and are checked when they're applied, days later perhaps. The same rules apply, plus merge strategies for fields like tags. See Proposals.

Proposals

A proposal is a changeset that hasn't been applied: updates, creates and destroys recorded against base versions, reviewed, then applied or rejected. It touches no live table until it is applied, so readers never see it.

Opening one

proposal = Retcon.propose(actor: member, message: 'New hours') do |p|
  p.update(venue, hours: 'Tue-Sun 4pm-2am')
  p.create(Event, venue_id: venue.id, name: 'Drag Bingo')
  p.destroy(old_event)
end
proposal.state      # 'proposed'
proposal.changes    # the diff to show a reviewer
  • p.update(record, fields) proposes new values. Its base is the version the record was loaded at, or pass base: seq (or {field => seq}) for the version the proposer saw.
  • p.create(Model, attributes) proposes a new record. Its id is chosen now (a UUID, or the next value of the table's sequence), so other parts of the same proposal can refer to it. It returns the unsaved record.
  • p.destroy(record) proposes deleting it.

Only versioned fields can be proposed. A proposal that changes nothing raises ArgumentError.

Reviewing

proposal.apply!(committer: reviewer)
proposal.reject!(by: reviewer, reason: 'Hours are wrong')
proposal.withdraw!                           # the author takes it back
amended = proposal.amend!(by: reviewer) do |p|
  p.update(venue, hours: 'Tue-Sun 5pm-2am')  # replaces the original's value for this field
end

apply! runs in one transaction: it locks the proposal, locks and catches up each record, checks every field against its base, writes the live rows, and marks the version rows applied with a fresh seq. Live rows are validated (an invalid result raises Retcon::Invalid), and model callbacks don't run (see Retcon.replaying? in Models).

If fields conflict, apply! raises Retcon::Conflict and applies nothing. To apply the rest:

result = proposal.apply!(committer: reviewer, on_conflict: :skip)
result[:conflicts]   # [FieldConflict]; also kept in the changeset's metadata as 'skipped'

Skipped fields stay in the applied changeset unapplied, so history shows what was proposed and not taken.

amend! keeps the author, makes the reviewer the committer, points the new proposal's parent at the original and marks the original amended.

Policy: commit, propose or deny

Retcon.edit sends an edit through a policy you define. Trusted editors commit directly, others open a proposal:

Retcon.policy = lambda do |actor, record, changes|
  next :deny if actor.record&.banned?
  next :commit if actor.record&.staff? || record.try(:owner_id) == actor.record&.id

  :propose
end

Retcon.edit(venue, { phone: '555-0100' }, actor: current_user, base: params[:retcon_seq].to_i)

changes is {field => [from, to]}. The policy returns :commit (an applied changeset), :propose (a proposal; the record is left unchanged) or :deny (raises Retcon::Denied). Trust tiers, matching rules and rate limits all fit here.

Routing reviews

Subscribe to proposal_opened to send proposals where they belong:

Retcon.on(:proposal_opened) do |proposal|
  ModerationQueue.enqueue(proposal, scope: proposal.scope)
end

Proposed rows in history

A proposal's version rows sit in the history tables with applied false and no seq. Heads, state and rebuilds only count applied rows, so an open proposal never changes what history says a record is.

Reverts

A revert undoes changesets the way an interactive rebase drops commits, without rewriting history: one new changeset of kind revert puts back what the dropped changesets replaced, and later work by others stays.

Retcon.revert(changeset, actor: staff)
changeset.revert!(actor: staff)                                  # the same
Retcon.revert_actor(vandal, actor: staff)                        # everything they authored
Retcon.revert_actor(vandal, actor: staff, since: 2.days.ago, scope: audience.id.to_s)

revert_actor takes every applied changeset the actor authored, leaving out their own reverts and redactions.

What a revert does

For each field the dropped changesets set:

  • if a dropped changeset wrote the field's current value, the field goes back to the newest value written by a changeset that isn't dropped (nil when there is none);
  • if someone else changed it afterwards, their value stays, and restoring the earlier value goes into a review proposal instead. This is a same-field overlap: a person decides.

Records the dropped changesets created are deleted (tombstoned). Records they deleted are revived, with their id and history. Fields nobody else touched are restored directly.

result = Retcon.revert_actor(vandal, actor: staff)
result.revert    # the applied revert changeset, or nil when there was nothing to undo
result.review    # a proposal with the overlaps, or nil; its parent is the revert
result.flagged   # [Actor] reviewers who applied the vandal's proposals

flagged lists committers who applied a dropped changeset someone else authored. They approved the damage, so whoever cleans up may want to look at what else they approved.

The review proposal fires revert_conflict as well as proposal_opened, so it can be routed like any proposal.

Undoing a revert

A revert is a changeset, so it can be reverted. That puts the dropped changes back, with the same rules about later work.

Reviving one record

To bring back a single deleted record without reverting anything else:

Venue.retcon_revive!(venue_id, actor: staff)

It reinserts the row with its id, every column from the tombstone snapshot and each field's newest version, as a changeset of its own (or in the open one). Reviving a record that is live raises Retcon::Error.

Rebuilding

Because live rows are a projection, any row can be rewritten from history:

Venue.retcon_rebuild!(venue_id)   # inserts, updates or deletes the live row to match history
Retcon.verify(Venue, sample: 500) # [[id, field, live, history], ...] for rows that disagree; empty when they agree

Drift and bulk writes

Not every write goes through a model save. update_all, insert_all, update_column, raw SQL and console fixes all write live rows without history. retcon finds them and records them before anything builds on them, attributed to Retcon::Actor.untracked, so history never silently disagrees with the live table.

How drift is found

version_table installs a trigger on the live table that sets retcon_dirty on any insert or update retcon didn't make. retcon's own writes set the retcon.writing setting for the transaction, so the trigger leaves them alone.

Drift is caught three ways:

  • On write. Before every update and destroy, retcon locks the row and, if it is dirty, writes a catch_up changeset with what changed. Your edit then goes in after it, in order.
  • Sweeps. Venue.retcon_sweep! catches up every dirty row in batches, and records rows deleted outside retcon (history says they exist, the live table has none) as tombstones. Run it from a scheduled job.
  • Full sweeps. Venue.retcon_sweep!(full: true) also compares every row's digest of its versioned fields with the one retcon wrote. That catches writes made with the trigger disabled. It reads the whole table, so run it rarely.

Rows with no history at all are pre-retcon data and get genesis changesets instead.

Venue.retcon_sweep!                          # => number of rows caught up
venue.retcon_drifted?                        # one row

Skipping history on purpose

Retcon.bypass { Venue.where(audience_id: old).update_all(audience_id: new) }

Writes in a bypass block skip history, but the trigger still marks the rows dirty, so the next sweep records them as untracked changes. Use bypass for migrations and repairs where attribution doesn't matter.

Bulk writes with attribution

Imports and syncs that would use upsert_all can keep attribution with Retcon::Bulk.upsert:

Retcon::Bulk.upsert(Venue, rows, unique_by: :external_key, actor: Retcon::Actor.named('import', 'facebook'))

Rows are matched to live rows by unique_by (one column or several). New rows are created, matched rows get only the fields that differ, and everything lands in one changeset of kind import. Like upsert_all, validations and callbacks don't run. It returns the changeset, or nil when nothing changed.

Redaction

Some things history must not keep: a phone number posted by mistake, a privacy or right-to-be-forgotten request, a takedown. Redaction is the one place retcon changes history rows, and it changes them only to delete a value.

Commitments

Every version row holds its value, a random salt, and a commitment: SHA-256 over the salt and the value's canonical JSON. Redaction deletes the value and the salt and keeps the commitment. History still verifies (each row proves a value existed, and which changeset wrote it), but the value is gone, and because the salt is gone too, a short value like a phone number can't be guessed back by hashing candidates.

row.verified?   # the commitment matches the value (true once redacted: nothing left to check)

Scrubbing a field

Retcon::Redaction.field(venue, :phone, actor: staff, reason: 'privacy request')

This scrubs the field from every version of the record, applied or proposed, and removes it from the record's tombstone snapshots. Options:

  • value: scrub only versions holding this value, leaving the field's other history alone.
  • remedy: the live value afterwards (nil by default), written as a new version so a rebuild lands on it. Pass Retcon::Redaction::KEEP to leave the live value alone when it is already clean.
Retcon::Redaction.field(venue, :phone, actor: staff, reason: 'posted by mistake', value: '555-0100',
                                       remedy: Retcon::Redaction::KEEP)

Every redaction is a changeset of kind redaction recording who, when, why and which version rows, never what was removed. It fires the redacted event.

Pseudonymizing an editor

Retcon::Redaction.editor(user, by: staff, reason: 'account deleted')

History stores actor ids, so this rewrites one actor row: their identity is replaced with a stable pseudonym such as editor-3f9a1c2b. Their edits stay, grouped under the pseudonym, so they can still be audited and reverted.

Deletion requests

result = Retcon::Redaction.erase(user, by: deletion_job, reason: 'deletion request')

For an automated personal deletion request, erase does three things in one transaction:

  1. reverts everything the person authored (see Reverts);
  2. scrubs every value they wrote from history;
  3. pseudonymizes them.

Later edits by other people to the same fields are not touched: they come back in result[:review] as a proposal, because a deletion request can't wipe other people's work. The result is { revert:, review:, flagged:, redaction: }.

Edges

Relationships between records (an episode recorded at an event, a person hosting a night) are often rows in a link table whose identity is the triple subject, predicate, object. Retcon::Edge versions them like any record and adds two rules: linking the same triple again revives the row it had, and removed edges leave the live table.

class EntityLink < ApplicationRecord
  include Retcon::Edge

  retcon_triple subject: %i[item_type item_id], predicate: :predicate, object: %i[target_type target_id]
end

A polymorphic end is [type_column, id_column]; a plain end is one id column. Give the table a unique index on the triple. discriminator: names one more identifying column, for a triple that may appear more than once (two slots on the same night, say).

Linking and unlinking

EntityLink.link!(episode, :recorded_at, event, status: 'linked')   # creates, updates or revives
EntityLink.unlink!(episode, :recorded_at, event)                   # tombstones; nil when there was no edge

link! updates a live edge in place, writing a version only for attributes that changed. If the triple was linked before and removed, it revives that row, keeping its id and its whole history, instead of starting a new one. It finds the old row through the tombstone snapshots, with a jsonb containment query on the history table's GIN index.

Walking the graph

Removed edges leave the live table, so anything that reads the live table, including graph_query, walks only live edges with no extra filter:

class MediaEpisode < ApplicationRecord
  graph_edge :recorded_at, to: Event, through: EntityLink, source: :item_id, target: :target_id,
                           where: { item_type: 'MediaEpisode', predicate: 'recorded_at', target_type: 'Event' }
end

graph_query sees only the links that exist now. Who linked or unlinked an edge, and when, is in its history like any other record.

Schema evolution

History outlives your schema. A column renamed today still has years of versions under its old name. retcon stamps every version row with the model's schema version and reads old rows through upcasters, so history never has to be rewritten when a column changes.

Versions and upcasters

Bump schema_version in the same deploy as the migration, and say how older rows read:

class Venue < ApplicationRecord
  include Retcon::Model

  versioned do
    schema_version 3
    rename_field :hours_text, :hours, before: 2     # rows written under version 1
    upcast(before: 3) do |field, value|             # rows written under versions 1 and 2
      next [] if field == 'legacy_rating'           # dropped
      next [['city', value['city']], ['region', value['region']]] if field == 'location'   # split

      [[field, value]]
    end
  end
end

An upcaster takes (field, value) and returns [[field, value], ...]: one pair to keep or rename, none to drop, several to split. Upcasters run in order of before:, and only on rows written under an older version, so a row from version 1 goes through both of the upcasters above.

Heads, state, conflict checks and rebuilds all read through upcasters. The rows themselves keep what was written, and row.raw_value returns it.

Changing columns

  • Adding a versioned column: nothing to do. Existing records have no versions for it until it changes. If the migration backfills it with SQL, the trigger marks those rows dirty and Venue.retcon_sweep! records the values.
  • Removing a column: add an upcaster that drops it, or ignore it first and remove it later.
  • Renaming: rename_field with the new schema version.
  • Changing a type: history keeps JSON values; an upcaster can convert old ones.

Live columns

version_table adds three columns to the live table. Keep them out of your forms and serializers:

Column Holds
retcon_seq the seq of the last changeset that wrote the row: its base version
retcon_digest a digest of the versioned fields as retcon last wrote them
retcon_dirty set by the trigger when the row is written outside retcon

Internals

Tables

create_retcon_tables makes:

  • the sequence retcon_seq, retcon's global order of application;
  • retcon_actors: kind, the record an actor stands for (ref_type, ref_id), a name, on_behalf_of_id for agents, and the pseudonym and redacted_at once redacted;
  • retcon_changesets: kind, state, author, committer, parent, scope, message, metadata, applied_seq, and when it was applied and decided.

version_table :venues makes retcon_venues, with one row per field change or lifecycle step:

Column Holds
changeset_id the changeset the row belongs to
record_id the live row's id, in the live table's key type
op set, or a lifecycle step: create, tombstone, revive
field, value for set: the field and {"v": value}; for a tombstone, the row as it was
salt, commitment for set: the salted SHA-256 commitment that survives redaction
applied, seq whether the changeset is applied, and its seq
base_seq the version the change was made against
schema_version the model's schema version when written
redacted_by_id the redaction changeset that scrubbed the value

History rows are inserted, never updated or deleted, except when a proposal is applied (applied, seq) and when redaction scrubs a value and salt.

One transaction

A save writes the changeset, the live row and the history rows in one transaction, in that order:

  1. lock the live row and catch up drift;
  2. check conflicts against the base;
  3. take the changeset's seq (on its first write), set the live row's retcon_seq, digest and dirty flag, and save;
  4. write the history rows for the fields that changed.

If anything raises, the transaction rolls back and neither history nor the live row changes. A catch-up that happens inside an open changeset renumbers that changeset after itself, so history orders the catch-up first.

Replaying

When retcon writes live rows from history (applying, reverting, reviving, rebuilding), it runs validations with Retcon.replaying? true and writes with SQL, so callbacks don't fire for changes that are old or were reviewed. Subscribe to changeset_applied for side effects that should follow these writes.

Cost

A save of N changed fields adds one changeset insert (per changeset, not per record), one multi-row history insert, one row lock and one DISTINCT ON query for the record's field heads. Reads of live tables are unchanged.
